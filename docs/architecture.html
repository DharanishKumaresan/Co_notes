Co notes Architecture

A shared notes board built for the most constrained host there is: PHP on shared hosting, no Composer, no build step, no long-lived process. Nearly every decision below is downstream of that.

The premise

The host is the architect

Co notes is a multi-board shared notes app. Everyone on a board sees the same cards and can read, edit, flag and delete any of them — the board is the unit of sharing, and there are no per-card permissions.

That product description explains almost none of the code. What explains the code is the deployment target: Hostinger shared hosting with phpMyAdmin. No shell guaranteed, no daemon, no package manager, no build pipeline. Three consequences propagate through every layer.

Forced by the host

No Composer → zero dependencies. Every line is first-party, including the Web Push cryptography. A spl_autoload_register closure in bootstrap.php maps CoNotes\Foo to app/Foo.php. That is the entire dependency system.

No build step → public_html/ is the deployable artifact exactly as it sits on disk. Nothing is transpiled, bundled or minified. The client is two files you can open in an editor.

No long-lived process → no WebSocket. Live collaboration runs over a cursor-based delta poll instead, which is the single most consequential decision in the codebase.

Physical layout

What is reachable by URL, and what is not

The most important line in the whole project is the boundary between public_html/ and everything beside it. Server code lives outside the web root, so a misconfigured Apache cannot serve .php source or the .env that holds the database password and the VAPID private key.

Request lifecycle

One entry point, one switch

There is no framework and no router library. Every request under /api/ is rewritten to a single PHP file, which locates the bootstrap, which loads the environment and hands the path to one switch over URL segments.

The front controller tries two bootstrap paths — ../../app/bootstrap.php for the correct layout, then ../app/bootstrap.php for a flattened upload — and returns a structured misconfigured JSON error if neither exists. That is a deployment concession, not architecture, but it turns the most common install mistake into a legible message instead of a white screen.

board_events

The sync spine

This is the heart of the system and the part most worth understanding. Shared hosting cannot hold a socket open, so there is no push channel from server to client. Instead every mutation appends a row to board_events, and that table's auto-increment id is the synchronisation cursor.

Clients poll GET /boards/:slug/changes?since=N and receive only what happened after event N. The client stores the highest id it has applied. There is no diffing, no timestamps, no clock comparison — just a monotonic integer that both sides agree on.

Two event types deliberately break the pattern

board.theme and board.renamed look like they should trigger a resync and do not. A theme is one attribute on <html> and a name is one string in the header; neither touches note data. So changes() returns the new value inline and the client repaints in place. Making them consistent with the others would mean reloading the whole board every time somebody picked a colour, once per second.

member.updated goes the other way and does force a full resync, because a profile change restyles that person's name and avatar on every card they have ever touched — a delta cannot express that.

Optimistic concurrency

The write path, and what makes it safe

The unit of write is a note, never the board. Each note carries an integer version; a PATCH carrying a stale version is rejected with 409 and the server's current copy, and the client offers Keep mine or Use theirs. No CRDTs, no operational transform — those are a different project.

Invariant

Every mutation appends to both note_edits and board_events, inside the same transaction as the write. A write that lands without its event is invisible to every other client; an event without its write is a phantom. Neither is recoverable after the fact, so they share a transaction.

Identity

One person, two names

Each user has a master profile, and optionally a different display name, colour and photo per board. The per-board override lives in nullable columns on board_members, where NULL means "inherit". Nothing is copied at join time, so editing the master profile updates every board that hasn't overridden it.

The resolution is a COALESCE, and it lives in exactly one place: app/Identity.php (90 lines). Every query that renders a person composes Identity::columns() and Identity::joins() — a card's last editor, its creator, the activity feed, the member list, the push feed.

A single query can carry two different people, which is what the alias arguments are for: Notes joins updated_by under u/bm and created_by under cu/cbm, then reads them back with Identity::fromRow($r, 'created_by', 'creator'). Add a new surface that renders a person without going through this and it will silently show master names while everything else shows board names — the failure is cosmetic, consistent, and very hard to spot.

public_html/assets/app.js

The client, without a framework

4,238 lines of plain ES, no build step, no virtual DOM. State is a dozen module-level variables and rendering is string templating into innerHTML. That sounds primitive and mostly is; it is also why the file opens in any editor and ships without a toolchain.

The network surface is deliberately narrow — 34 call sites, all through one api() helper and a small group of functions marked "the seam". Everything else in the client is ignorant of HTTP.

Saves in flight

The subtlest code in the client is four lines. flushSave() samples an editSeq counter before the request and compares it after: if it moved, the user typed while the save was in the air, so the server's response must not replace their newer text. Instead the client keeps the local text, takes the server's new version number, and saves again. Remove that comparison and typing during a slow save silently loses keystrokes.

Search is client-side, on purpose

The API hands the client every live card for the open board up front, so a search endpoint would be a second source of truth for data already in memory — and it keeps working offline. The tradeoff is stated plainly: it covers the open board's live cards only, not the trash and not other boards. If a board ever outgrows the client's memory, this is the first thing that has to move server-side, along with the delta sync.

notes.content

Formatting that is text all the way down

Cards support bold, italic, underline, headings, bullets and checklists. None of it is stored as HTML. The content column holds a small markdown subset as plain text, and that is a security decision before it is a formatting one: the board is shared, so storing HTML would mean sanitising one member's input before showing it to everyone else on their board.

Because it is text, the server needed no changes at all — Validate::clean() only strips control characters, so every marker survives the round trip untouched.

XSS invariant

renderRich() escapes first and applies markers second. Never the other way round, or a card becomes an XSS vector for everyone on the board.

Why the editor has a mirror

A <textarea> renders in exactly one font — it cannot show part of its text as bold. So the editor paints its own formatting: #e-content is a transparent textarea sitting over #e-mirror, a styled copy of the same string. The textarea still owns the caret and is still the source of truth, which is the point — the save path, the 409 flow and the plain-text invariant all read eContent.value and none of them had to move. A contenteditable would have touched every one of them.

The constraint this creates is absolute: the mirror may not change any glyph's advance width. If the mirror lays a character out even slightly wider, the painted text slides out from under the caret, worsening with every character on the line. Measured on this stack, a real font-weight: 750 costs +17.9 px across one line of prose. So bold is faked with -webkit-text-stroke, headings are not enlarged, and markers are dimmed to 30% rather than hidden — their width still has to be there.

Italic is the interesting case. It is free only when the resolved face has no italic of its own and the browser shears the upright instead. Measured: Inter drifts 0 px, the system font stack 4.2 px. So italicIsMetricSafe() measures once at runtime and only then adds .italic-ok — which means the editor slants italic on some platforms and silently does not on others, including every Apple device, where SF Pro has always had a true italic.

app/Push.php · 701 lines

Web Push with no crypto library

The largest single class in the project exists because of the no-Composer rule. Web Push normally means encrypting a payload with ECDH key agreement, HKDF and AES-128-GCM against the browser's public key — a lot of hand-rolled cryptography to get subtly wrong.

The way out is that a push is allowed to carry no payload at all. Co notes sends a signed "wake up" and nothing else; sw.js then calls GET /api/push/pending over ordinary authenticated HTTPS and finds out what happened. The only cryptography left is the VAPID JWT — one openssl_sign(), plus DER wrangling to rebuild the EC key and reshape the signature into the raw form the spec wants.

The cost is that the browser must be online to display the notification, which for a shared board is no cost at all.

Four triggers, two kinds

Somebody flagged a card
Goes to everyone except the person who did it. It is news about another person.
Somebody added an event
Same — excludes the actor.
A card came due
Goes to everyone including whoever set the date. A reminder is not news about a person; it is the thing itself arriving, and whoever wrote "call the tiler Thursday" is exactly who needs telling on Wednesday.
An event is coming up
Same — nobody is excluded.

Reminders need their own marker because nobody acted, which is what reminded_at on notes and calendar_events is for. It is stamped in the same UPDATE that selects the row, which is what makes tools/remind.php safe to cron as often as you like. It is deliberately not the existing userless note_edits row with action = 'due': that one fires on the due date and a reminder fires before it, so one marker cannot mean both — and overloading it would have made unflagging a card silently re-arm its reminder.

A subscription is a browser, not a person. The same user on a phone and a laptop is two rows, and both buzz.

sw.js

The shell, and the versioning that keeps it honest

The service worker caches the shell so the app opens without a network. That is all it may do — /api/ is never cached, and neither is /uploads/. A card served from disk would be a lie about what everyone else on the board can see, and it would sit behind the version checks that stop two people clobbering each other.

A bug that shipped

Navigations are network-first; assets used to be cache-first with a background refresh. So for one launch after every deploy, the browser ran the new index.html against the previous app.js. The new markup had a button in it that the old script had no handler for, so the button was visibly present and did nothing — and the second launch fixed itself, which made it look intermittent rather than broken.

The fix is that shell assets now carry ?v=N, matched to VERSION and CACHE in sw.js. A versioned URL cannot be answered from a cache that predates it, so markup and script can no longer disagree. Bumping CACHE alone was never sufficient. tools/doctor.php fails if the numbers drift apart.

Migrations are forward-only and numbered 001 to 008. Order is load-bearing: 003 drops board_members.theme, 004 alters notes, 005 depends on the table 004 leaves behind. Only 007 is safe to re-run.

Deploy ordering

Deploying code before running its migration takes the site down. Every board query names the columns the migrations add, so PHP one migration ahead of the database errors on every request until the SQL is imported. Import first, or accept a window of downtime.

Deliberate omissions

What is not built, and why

No password auth
OAuth only — Google and GitHub. No password to store, leak or reset.
No per-card permissions
The board is the unit of sharing, by design. Everyone on a board can edit everything on it.
No WebSocket
Shared hosting cannot hold one open. See the sync spine.
No CRDT or OT
Optimistic versioning with a visible conflict instead. Real merge semantics are a different project and would need to be their own decision.
No board restore UI
A deleted board is recoverable for 30 days by clearing deleted_at by hand, then hard-deleted by cleanup.php. Cascades take the cards, calendar, members and history with it.
Timezone conversion on calendar dates
Deliberately absent. event_date is a DATE and start_time a TIME, neither carrying a zone — the one place in the app that is not UTC over the wire. A shared calendar wants "14 March, 3pm" to read the same for everyone; converting per viewer would have two people on one board disagreeing about which day something falls on.

Honest status

What has actually run

The PHP is php -l clean and has been exercised against a real MariaDB: board load, the note shape, the 409 conflict path, the reminder sweep and the push feed. The client is driven end to end against a mock API that stubs the whole backend in memory, so the frontend runs from disk with no PHP, no MySQL and no OAuth.

What has not run: real push delivery through Google's and Apple's services, which needs an HTTPS origin and a physical phone; the reminder cron on an actual schedule; OAuth against a production domain; GD photo uploads on the host's PHP; and two people editing the same card at the same time. Each is blocked on the same thing — a live deployment with working sign-in — and none can be simulated from a development machine.
